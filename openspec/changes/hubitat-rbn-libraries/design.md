## Context

See proposal.md for motivation. The facts that shape the approach, all verified against `kkossev/Hubitat@0bf47407` and the current repo:

- **Upstream layout.** Libraries are flat files in `Libraries/`, each opening with a `library(base:, author:, category:, description:, name:, namespace:, importUrl:, documentationLink:, version:)` block. Drivers are a small source (`#include kkossev.<lib>` lines after the imports) plus a hand-made `<Driver>_lib_included.groovy` bundle. Upstream's `AGENTS.md` states there is no build script; the bundle is regenerated by copy-paste.
- **Bundle format.** In the Cube bundle the five `#include` lines become five empty lines (source is 383 lines; the `Libraries` banner is line 384), so driver line numbers are identical in source and bundle. Each library sits between `// ~~~~~ start include (144) kkossev.commonLib ~~~~~` / `// ~~~~~ end include (144) kkossev.commonLib ~~~~~` and every body line ends with `// library marker kkossev.commonLib, line N`. The `(144)` is the library's code id on kkossev's own hub (`Libraries/.hubitat/metadata.json`), meaningless anywhere else. No library includes another library.
- **Dispatch contract.** `commonLib.parse()` (line 152) calls `isTuyaE00xCluster()` and `otherTuyaOddities()` on every message before `myParseDescriptionAsMap`, then `standardAndCustomParseCluster()` (line 231) builds `"customParse${ClustersMap[cluster]}Cluster"` / `"standardParse…Cluster"` and resolves them with `respondsTo()`. Handler names, Hubitat lifecycle methods, and capability commands are therefore fixed camelCase identifiers. A driver cannot define its own `parse()` — a method defined in both driver and library is a compile error.
- **Tuya surface in the five Cube libraries.** `commonLib`: `isTuyaE00xCluster`, `otherTuyaOddities` (call at line 179), the `CLUSTER_TUYA`/`SETDATA`/`SETTIME`/`TUYA_*`/`DP_TYPE_*` getters (760–777), `syncTuyaDateTime`, `standardParseTuyaCluster`, `standardProcessTuyaDP`, `getTuyaAttributeValue`, `getTuyaCommand`, `sendTuyaCommand`, `getZclSeqNo`, `getPACKET_ID`, `tuyaTest` (plus its `_DEBUG` command at 67–70), `tuyaBlackMagic`, `queryAllTuyaDP`, `isTuya()` (1610), `updateTuyaVersion` (1618), the `clusterInt == CLUSTER_TUYA` branch in `parseDefaultCommandResponse` (460), the `isTuya()` block in `configure()` (1290), calls to `updateTuyaVersion()` in `initialize()` (1334) and `checkDriverVersion()` (1392), and `0xEF00: 'Tuya'` in `ClustersMap` (225). `onOffLib`: the `sendTuyaParameter` branches in `on()`/`off()` (108–117, 141–150). `batteryLib`: the `isTuya()` branch (61) and `tuyaToBatteryLevel`/`handleTuyaBatteryLevel` (157–175). `xiaomiLib` and `buttonLib` have none. `levelLib`, `energyLib`, `reportingLib` have none.
- **Aqara surface stays.** `aqaraBlackMagic()`, `updateAqaraVersion()`, `isAqara()`, and all of `xiaomiLib` are what the Cube runs on.
- **Cube driver.** No Cube is currently paired to the hub (join fails at the initializing step, before driver selection). `Drivers/Aqara Cube T1 Pro/Aqara_Cube_T1_Pro.groovy`, 383 lines, version 3.3.0 (2026-08-27), includes `commonLib onOffLib xiaomiLib buttonLib batteryLib`, defines `customRefresh`, `customInitializeVars`, `customInitEvents`, `customConfigureDevice`, `customParseMultistateInputCluster`, `customParseAnalogInputCluster`. Its only upstream-identity references are the five `#include` lines, `importUrl`, `namespace`, and `author`. The copy at `hubitat/drivers/aqara-cube-t1-pro.groovy` is the upstream bundle at the same version.
- **Hubitat naming rule.** The library-definition documentation states `name` and `namespace` may contain letters, digits, dots, dashes, and underscores, and that `namespace.name` must be unique per hub. Groovy 2.4 identifiers cannot contain dashes.
- **Repo conventions that bind here.** Rules are `<dir>/AGENTS.md` with `paths:` frontmatter, linked by a relative symlink from `.agents/rules/<name>.md` (`.claude/rules` is itself a symlink to `.agents/rules`). Root `justfile` loads modules with `mod <name> "<path>"`. `uv` manages Python 3.13 with the `homelab` package at `src/homelab/`. `treefmt` has no Groovy formatter. The pre-commit config is generated by git-hooks.nix and is not hand-edited. The repo's pre-tool-use hook denies any written file containing a literal parent-directory path segment, so the symlink target is described in words here and created by the apply phase.
- **Repo is public** (`gh repo view jmuchovej/homelab` → `PUBLIC`), so the hub can fetch `raw.githubusercontent.com` URLs into this tree.

## Goals / Non-Goals

**Goals:**

- A `hubitat/` tree whose authored surface is small files (`libraries/*.groovy`, `drivers/<d>/<d>.groovy`) and whose hub-facing surface is generated bundles, with a mechanical, checkable path between them.
- A `common` library whose per-message cost contains nothing Tuya, while every `custom*`/`standard*` hook name and every public command and attribute the Cube driver relies on is preserved byte-for-byte.
- Provenance a reader can follow from any forked file back to the exact upstream line.

**Non-Goals:**

- Adding `0xFC31` (Inovelli) to `ClustersMap` or any other VZM31-SN-specific change. That is the next change; this one only guarantees the base compiles and runs.
- Forking `deviceProfileLibV4` or `groupsLib`.
- Removing the `kkossev.*` libraries or driver from the hub.
- Groovy linting or formatting in `treefmt`.
- Wiring the drift check into pre-commit (would require a git-hooks.nix change).

## Decisions

### D1. Library names are the bare domain word, no `lib` suffix, included as `#include rbn.<name>`

`hubitat/libraries/common.groovy` declares `name: 'common'` and is included as `#include rbn.common`: on-disk name, `name:` field, and include token are one string, and the directory already states the kind, so upstream's `Lib` suffix carries no information. The mapping from upstream is `commonLib→common`, `onOffLib→switch`, `xiaomiLib→xiaomi`, `buttonLib→button`, `batteryLib→battery`, `levelLib→level`, `energyLib→meter`, `reportingLib→reporting`. `switch` is chosen because the library implements exactly Hubitat's `Switch` capability over cluster `0x0006` and nothing else; `power` was considered and rejected because the metering library is the one that declares `PowerMeter`/`EnergyMeter`, so the name would point at the wrong file, and dimming is `levelLib` (`SwitchLevel`/`ChangeLevel`), which stays a separate library as upstream keeps it. `meter` replaces `energy` because the library declares `PowerMeter`, `EnergyMeter`, `VoltageMeasurement`, and `CurrentMeter` over clusters `0x0702` and `0x0B04`; "energy" names one of its four readings and invites the same power-versus-energy confusion that ruled out `power` for the switch. Merging `switch` and `level` into one library was raised and tabled: it would pull dimming into the Cube's bundle and widen the upstream diff for both files, and nothing in this change needs it. Every name in this change is a single word, so no dash reaches the hub; kebab-case remains the rule for a future two-word library (Hubitat's documented `name` character set includes dashes), to be verified on the hub when the first one is created. Alternative rejected: camelCase `name:` with kebab filenames — two names for one thing that the bundler would then have to map.

### D2. Groovy identifiers stay camelCase

Lifecycle methods (`parse`, `installed`, `updated`, `configure`, `refresh`, `initialize`), capability commands (`on`, `off`, `setLevel`, `push`, `hold`, `release`, …), and the reflective `customParse<Cluster>Cluster` / `standardParse<Cluster>Cluster` / `custom*` hook names are contracts with the platform or with the dispatcher; renaming any of them silently stops dispatch (no error, the handler is simply never found). snake_case is legal Groovy but would apply only to private helpers, producing a file with two conventions on adjacent lines. Kebab-case applies to filenames, library names, directory names, `just` recipes, and any future JSON profile keys.

### D3. Strip scope is exactly the Tuya call graph, and `0xEF00` is the only `ClustersMap` entry removed

Remove every item enumerated under "Tuya surface" in Context; keep every Aqara item. `ClustersMap` keeps `0xE001`, `0xE002`, `0xEC03`, `0xED00`, `0xFC03`, `0xFC11`, `0xFC80`, `0xFC81`: they have no handler in the forked set either way, and leaving them keeps the diff against upstream minimal for future syncs. With `0xEF00` gone the dispatcher's own "unknown cluster" warning covers a Tuya message, which is the spec's required behaviour. `onOfInitializeVars`, `batteryInitializeVars`, `energyInitializeVars` and the other `executeCustomHandler` names in `initializeVars()` are left untouched even where the corresponding library is not included — `executeCustomHandler` is `respondsTo`-guarded and this is how upstream works. The `intTo16bitUnsignedHex`/`intTo8bitUnsignedHex` helpers sit under a Tuya banner comment but are generic and are kept.

### D4. Each forked library keeps its upstream `version:` and gains a provenance block; the Cube driver gets a new `timeStamp()`

Library `version:` strings are informational (nothing compares them). Replacing them would break the one thing they are good for — telling which upstream release a file descends from. Provenance is a fixed-format comment directly under the Apache header:

```
 * Forked from https://github.com/kkossev/Hubitat (Libraries/commonLib.groovy) at commit 0bf47407.
 * Modified for the rbn namespace: <one line per class of change>.
```

`checkDriverVersion()` compares `version() + timeStamp() + …`, so the Cube driver changes `timeStamp()` and appends a history line; that triggers a benign `initializeVars(false)` on first parse after the switch, which is the upstream upgrade path.

### D5. Bundler is one stdlib-only Python script under `hubitat/`, run from the `hubitat/justfile` module

`hubitat/scripts/bundle.py`, executed as `uv run python hubitat/scripts/bundle.py [--check] [driver-source…]`, defaulting to every `hubitat/drivers/*/*.groovy` that does not end in `.bundled.groovy`. Stdlib only, so no `pyproject.toml` change and nothing to lock. Alternatives: a `homelab hubitat` Typer subcommand (couples a 60-line transform to the CLI package and its release cadence; can be promoted later if a second consumer appears) or nushell (matches the hooks, but the repo's stated preference for tooling is Python, and the `uv` toolchain is already present). The `just` module is `mod hubitat "hubitat/justfile"` at the root with recipes `bundle` and `check`; `check` bundles to memory and diffs against the committed file, exiting non-zero and naming each stale bundle.

### D6. Bundle format reproduces upstream minus the hub-local id

Include lines become empty lines (line-number preservation is what makes hub error messages for the driver body useful without translation). Then the upstream banner line, then per library: empty line, `// ~~~~~ start include rbn.<name> ~~~~~`, the body with `// library marker rbn.<name>, line N` appended to every line, `// ~~~~~ end include rbn.<name> ~~~~~`. The `(NNN)` hub code id is dropped: it is unknowable off-hub and differs per hub. The bundler rejects a missing library, a nested `#include`, and any library containing `'''` or `"""` — a per-line suffix inside a multi-line string would change the string. No current library has one; the check keeps that true.

### D7. Validation in this change is compile-only; runtime validation is its own follow-up change

No device the fork could run on is usable for validation right now: the Cube fails Hubitat's join before driver selection (a ZDO-discovery problem, not a driver one — usually the device falling asleep mid-pair), and the paired Inovelli dimmers have no `rbn` driver. Writing even a minimal VZM31-SN driver here to obtain a test subject was considered and rejected: it pulls the next change's scope into this one, and testing it means temporarily stripping scenes and LED notifications from an in-service switch. So this change proves two things and claims no more: every library compiles (Hubitat compiles the whole bundle on save, so a dangling reference from the strip surfaces as a save error with a marker-mapped line), and the Tuya surface is absent from the source (grep-level scenarios in the spec). Mechanism: the Cube bundle compiles `common`, `switch`, `xiaomi`, `button`, `battery`; an uncommitted include-all probe driver (source kept only long enough to bundle and save it) compiles all eight together, then is deleted from the hub. `hubitat/AGENTS.md` records the probe procedure. The follow-up change owns runtime scenarios — single-dispatch refresh, Tuya-free parse logs, Cube gestures — on whichever device is first available.

### D8. `importUrl` targets the bundle on `main` via raw GitHub

`https://raw.githubusercontent.com/jmuchovej/homelab/main/hubitat/drivers/<driver>/<driver>.bundled.groovy`. The repo is public and the hub can fetch it, which removes any dependency on HPM for these drivers. Bundles are therefore committed, and `just hubitat check` is what keeps them honest until a hook can. Rejected: a `repository.json` / `packageManifest.json` HPM manifest — extra surface for a single-user repo; can be added later without changing anything here.

### D9. `deviceProfileLibV4` is not forked in this change

It is 2,623 lines; its conversion core (`compareAndConvertTuyaToHubitat*`, `processTuyaDPfromDeviceProfile`, `sendTuyaParameter`) is datapoint-shaped, though it also carries a ZCL-attribute path (`processClusterAttributeFromDeviceProfile`, `zclWriteAttribute`) that an Inovelli driver could use. Whether the VZM31-SN driver wants that library, a trimmed fork of it, or a static parameter map is a decision that needs the driver in hand; forking it now means stripping a library with nothing to compile it against.

### D10. Existing `hubitat/` files: replace the Cube, leave the rest

`hubitat/drivers/aqara-cube-t1-pro.groovy` (the upstream bundle) is deleted; its replacement is the ported driver directory. `hubitat/drivers/inovelli-dimmer-blue-series-VZM31-SN.groovy` is the driver currently running the user's switches and is replaced by the VZM31-SN change, not this one. `home-assistant-hub-parent.groovy`, `home-assistant-device-bridge.groovy`, and `inovelli-zigbee-bindings.groovy` are unrelated third-party code and are out of scope; the README notes their provenance only insofar as it already appears in their headers.

### D11. `hubitat/AGENTS.md` is the single rule for the tree

Contents: the source-vs-bundle rule (edit sources, run `just hubitat bundle`, never edit a `.bundled.groovy`); the naming contract from D1/D2 with the reason; the hook protocol (`customParse<Cluster>Cluster` beats `standardParse…`, resolved by `respondsTo`; `ClustersMap` is the registry a new private cluster must be added to); `sendZigbeeCommands()` as the only way to emit commands and why; the 64 KB per-method compile ceiling; provenance and the sync procedure (diff upstream `Libraries/<lib>.groovy` between the pinned sha and HEAD, apply by hand, update the sha in the provenance line and README); the list of what was stripped so it is not re-added by reflex; the throwaway include-only driver procedure from D7; and the no-`vendor/` rule. Linked as a relative symlink at `.agents/rules/hubitat.md` pointing two directories up to `hubitat/AGENTS.md`, and `jj file track`ed. No other rule changes.

### D12. Work happens in the main checkout, committed with explicit filesets

Nothing here is evaluated by Nix, so a worktree buys no isolation, and hub testing is copy-paste from the working tree either way. The main checkout carries many unrelated uncommitted files; the commit is made with explicit paths (`hubitat/`, `.agents/rules/hubitat.md`, `justfile`, `openspec/changes/hubitat-rbn-libraries/`) so none of them ride along.

## Risks / Trade-offs

- [Hub rejects a dash in a library `name`] → Not reachable in this change: all eight names are single words. The first two-word library verifies the rule on the hub before it is committed; if rejected, that library alone takes a one-word or underscore name.
- [Strip removes something a kept function calls] → Hubitat compiles the whole bundle on save, so a dangling reference surfaces as a save error naming the bundle line, which the marker maps to a library line. `respondsTo`-guarded call sites cannot dangle.
- [A runtime regression from the strip is invisible until the follow-up change] → Accepted knowingly. The strip is bounded to the enumerated call graph, every deletion is grep-verified for dangling callers, and the hub compile catches anything the grep misses. The follow-up change's first task is the runtime pass, so the exposure window is one change.
- [Nothing on the hub changes driver, so nothing can regress] → Rollback for this change is deleting the eight libraries and one driver entry from the hub, none of which any device uses.
- [Bundles and sources drift] → `just hubitat check` exists from day one; wiring it into pre-commit is a follow-up because the hook config is generated by git-hooks.nix.
- [Marker suffix corrupts a line] → Only multi-line string literals are at risk; the bundler refuses libraries containing them. Block comments and line comments absorb a trailing `//` harmlessly, as upstream's identical practice shows.
- [Upstream sync cost grows] → Accepted for `common`; the other seven stay near-verbatim. The provenance sha makes the three-way diff mechanical.
- [`importUrl` points at `main` before the change lands there] → The URL is only useful after push; until then the bundle is pasted into the hub. This is the same for every driver in the tree and is noted in the README.

## Migration Plan

1. Hub, libraries: save all eight `rbn.*` libraries under Libraries Code (order does not matter; nothing includes them yet).
2. Hub, compile proof: save the throwaway include-all driver, confirm it saves, delete it.
3. Hub, Cube driver: save `aqara-cube-t1-pro.bundled.groovy` under Drivers Code and confirm it saves. No device is moved onto it.
4. Rollback: delete the driver and library entries added in 1–3. No device references them.
5. Repo: commit; after push, confirm the raw URL serves the bundle by importing it once via URL into the driver entry.
6. Follow-up change (not this one): runtime validation on the first available device — a minimal standard-cluster VZM31-SN driver on one dimmer, or the Cube once it pairs — covering single-dispatch refresh, Tuya-free parse logs, and the Cube gesture scenarios.

## Open Questions

- Whether to wire `just hubitat check` into pre-commit via git-hooks.nix once the tree has more than one driver. Deferrable; does not change the specs or tasks here.
- Whether the `kkossev.*` libraries and driver should be removed from the hub after a soak period. Deferrable; the spec does not depend on their absence.
- Which device carries the follow-up runtime validation, and whether that change is the minimal VZM31-SN driver itself or a precursor to it. Deferrable; the compile-only contract here does not depend on the answer.
- Whether `switch` and `level` should become one library. Tabled at planning; revisit when the VZM31-SN driver shows how much of `level` a dimmer actually uses alongside `switch`. Does not change the specs or tasks here.
