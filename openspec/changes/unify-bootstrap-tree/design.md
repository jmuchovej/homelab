## Context

See proposal.md for motivation.
Facts that shape the approach, all observed in the working copy on 2026-10-02:

- `flake.nix` is generated by `flake-file` from `modules/inputs.nix`; its outputs template is `inputs.import-tree ./modules`.
  The pinned `import-tree` (`eb1b52e`) flattens list arguments (`flatten = x: if isList x then concatMap flatten x else [ x ]`), so `import-tree [ ./modules ./bootstrap/nix ]` is supported without any other change.
  import-tree skips `_`-prefixed paths and imports every other `.nix` file as a module.
- The working-copy `bootstrap/` holds two kinds of files.
  Live, consumed by committed Nix: `kubernetes/{cilium,cilium-values,flux-operator,flux-instance,flux-agekey}.yaml`, `kubernetes/checks.nix`, `talos/machineconfig.yaml`.
  Stale duplicates: `bootstrap.nix` (lacks the `_:` module wrapper, four-hop relative path escapes the repo), `iso.just` (older than `modules/hosts/bootstrap/justfile`, which gained `[script]` and `set script-interpreter`), `mikrotik.just` and `rbn-bootstrap.rsc` (comment-only drift from `mikrotik/bootstrap/`, minus the disabled SSH-host-key block).
  The canonical sources are `modules/hosts/bootstrap/*` and `mikrotik/bootstrap/*`.
- Just 1.58.
  Recipes in a submodule run with the submodule's directory as cwd; `justfile_directory()` is the root justfile's directory; `source_directory()` is the submodule file's directory.
  A nested `just <recipe>` from a submodule's cwd finds the submodule's own `justfile` and loads it standalone, which re-roots `justfile_directory()`.
  That is why `mikrotik/bootstrap/` carries `secrets` and `topology.yaml` symlinks today, and why its `uploads` recipe's fallback to `just render` is fragile.
- The MikroTik `render` step reads `root-password` and `tofu-password` from `secrets/hosts/<dc>-<relay>.sops.yaml`; the `wait` step reads `network.<relay>.terraform-password` from `secrets/<dc>.sops.yaml`.
  Both keys exist.
  They are two copies of the credential the `terraform` RouterOS user is created with.
- `src/homelab/commands/_bootstrap.py` does four things: decrypt `host-key` with `sopsy`, convert it PKCS#8 → OpenSSH with `cryptography`, run `nixos-anywhere` via `nix run github:nix-community/nixos-anywhere`, and ping until the host answers.
  Its `host_dir` is `src/modules/hosts/<name>` (stale since the flatten).
  `sopsy` is not in nixpkgs; `cryptography` is also used by the CA commands.
  Typer flattens the unnamed sub-app, and the ISO banner advertises `homelab bootstrap host <name> <ip>`, which matches neither.
- `secrets/keys/` is untracked in its entirety: `iso-key` (OpenSSH private key), `iso-key.pub`, `iso-key.age.pub`, `1p-homelab.pub`.
  `.gitignore` already negates `secrets/**/*.pub`, so the public keys are trackable; jj auto-track is off, so nothing is tracked until `jj file track`.
  The ISO aspect reads `iso-key.pub` at eval time.
- The devshell (`modules/devshell/shells.nix`) has `nushell-plugged`, `sops`, `gettext`, `uv`, `python313`; it does not have `nixos-anywhere`.
  `ssh-keygen` is on every host via OpenSSH.

## Goals / Non-Goals

**Goals:**

- Every bootstrap path has one home, is tracked, and is reached by path.
  A clean clone evaluates `bootstrap`, `da-vcx-1`, and `en-t65-1`.
- Each `bootstrap/<target>/` works via the root justfile and standalone (`just -f bootstrap/<target>/justfile …`) without symlinks or recursive `just`.
- The install flow is a recipe with the same behavior as the Python it replaces, minus the stale path and the two Python-only dependencies.

**Non-Goals:**

- Re-bootstrapping any device, host, or cluster.
  Nothing here touches live state.
- Teaching Talos to consume the k3s seed manifests.
  The seam is documented; the consumer does not exist yet.
- Rewriting the existing bash ISO recipes in nushell, or fixing the stale documents, `.sops.yaml` rule, `_misc.py` scanner, or docs-site CLI pages listed in the proposal's Impact.
- A `bootstrap/kubernetes/justfile`.
  The directory is data; its only consumer is Nix.
  Verification of a seeded cluster is `kubectl`/`flux` by hand, as today.

## Decisions

**D1. Discovery: a second import-tree root, not a stub module.**
`flake-file.outputs` in `modules/inputs.nix` becomes `inputs.import-tree [ ./modules ./bootstrap/nix ]`, and `nix run .#write-flake` regenerates `flake.nix`.
Alternative: leave a one-line `imports = [ ../../../bootstrap/nix/iso.nix ]` stub at `modules/hosts/bootstrap/bootstrap.nix`.
Rejected by the user: a stub is a second place to keep in sync and contradicts "everything bootstrap-related lives in `bootstrap/`".
Consequence: `bootstrap/nix/` is the only auto-discovered directory outside `modules/`, so it must contain only flake modules (today: `iso.nix`) plus non-`.nix` files (`justfile`).
Any helper `.nix` that is not a module goes under a `_`-prefixed name.
`bootstrap/kubernetes/checks.nix` is unaffected because `bootstrap/kubernetes/` is not a root.

**D2. The ISO aspect moves verbatim, with two edits.**
`modules/hosts/bootstrap/bootstrap.nix` → `bootstrap/nix/iso.nix`, keeping `den.hosts.x86_64-linux.bootstrap` and `den.aspects.bootstrap` (the `nix-builders` exclusion list and `just bootstrap nix test/make` depend on the name).
Edits: both `lib.fileContents ../../../secrets/keys/iso-key.pub` become `lib.fileContents "${inputs.self}/secrets/keys/iso-key.pub"` (the file takes `{ inputs, ... }` instead of `_:`), matching how `kubernetes.nix` and `talos.nix` reach repo data and removing hop-counting; and the banner's install line becomes `just bootstrap nix install <name> <addr>`.
Alternative: keep the relative path with two hops.
Rejected: the repo already uses `inputs.self` for every cross-tree reference from Nix, and the repo-layout spec's "relative paths" scenario was only ever about this one file.

**D3. Install is a nushell recipe; the Python command is deleted.**
`just bootstrap nix install host addr key=<default> *flags` reproduces `_bootstrap.py`:

- Preconditions: `modules/hosts/<host>/<host>.nix` exists (no `mkdir`; a host that is not in the flake cannot be installed); confirmation via `gum confirm` unless `--yes`; the iso-key private path exists (parameter, default `secrets/keys/iso-key`, which is where the operator keeps it today; the Python read `$RBN_ISO_KEY` only).
- Staging: `mktemp -d`; copy `modules/hosts/<host>/root/` into it if present; `sops -d --extract '["host-key"]' secrets/hosts/<host>.sops.yaml` → `etc/ssh/ssh_host_ed25519_key` (0600); if the first line is a PKCS#8 header (`-----BEGIN PRIVATE KEY-----`), `ssh-keygen -p -N '' -f <that file>` rewrites it in place as OpenSSH format; `ssh-keygen -y -f` writes the `.pub` and doubles as the format check.
  This removes both `sopsy` and the `cryptography` use.
  Two facts found during apply: the Python called `load_ssh_private_key`, which accepts only OpenSSH-format keys, so the NixOS host keys in sops are already OpenSSH format and the PKCS#8 branch is a safety net (the RouterOS relay keys are the PKCS#8 ones); and Apple's `ssh-keygen` rejects PKCS#8 with "invalid format" while nixpkgs' OpenSSH 10.5 (OpenSSL-linked) converts it, so `openssh` joins `nixos-anywhere` in the devshell and the recipe relies on the devshell `PATH`.
- Run: `nixos-anywhere --flake .#<host> --generate-hardware-config nixos-facter modules/hosts/<host>/facter.json --target-host root@<addr> --extra-files <stage> -i <key> --ssh-option IdentitiesOnly=yes`, cwd = repo root, with `nixos-anywhere` from the devshell (pinned by nixpkgs) rather than `nix run github:…` (unpinned, network at run time).
- Wait: poll `nc -z <addr> 22` with a timeout, not `ping` (`ping -W` differs between macOS and Linux, and SSH answering is what the operator needs next).

Alternatives: a hubitat-style uv workspace package under `bootstrap/nix/` (rejected by the user: `sopsy` is not in nixpkgs and the logic is four shell commands); keep `homelab bootstrap` and shell out to it (rejected: leaves the stale path and the dependency in place and splits the flow across two trees).
`secretspec` as the source of the iso-key private key is deferred (see Open Questions): it would supply an env var, and `ssh -i` needs a file, so it changes nothing about the recipe's shape.

**D4. Just layout: `bootstrap/justfile` → `nix`, `mikrotik`.**
Root: `mod bootstrap "bootstrap/justfile"` replaces the `modules/hosts/bootstrap/justfile` line; the root `facter` recipe is deleted (it moves to `bootstrap/nix/justfile`, since it is the post-install step of bringing a host up and `install` writes the same file).
Root `mod mikrotik "tofu/mikrotik.just"` is unchanged: those are tofu-side REST helpers, not bootstrap.
`bootstrap/justfile` is `mod nix "nix/justfile"`, `mod mikrotik "mikrotik/justfile"`, and a `[private] default` that lists.
Existing bash ISO recipes (`test`, `make`, `sync`, `install-ventoy`) are carried over unchanged from `modules/hosts/bootstrap/justfile`, including their `[no-cd]` (they must run from the invocation directory so `.#` and `result/` resolve at the repo root).
New recipes (`install`, `facter`) are nushell via `[script("nu")]` so the file can mix interpreters without a file-wide `script-interpreter` that would break the bash recipes.

**D5. MikroTik recipes locate the repo root from their own file.**
`bootstrap/mikrotik/justfile` defines `root := parent_directory(parent_directory(source_directory()))` and derives `secrets := root / "secrets"`, `topology := root / "topology.yaml"`, `template := source_directory() / "rbn-bootstrap.rsc"`.
This works when invoked through the root justfile and when invoked standalone, so no symlinks are needed and the directory is self-contained.
The `just sops` / `just scp` / `just ssh` helper recipes and the `uploads` fallback to `just render` are replaced: step ordering becomes recipe dependencies (`upload dc relay ip: (render dc relay)`, `run dc relay ip: (render dc relay) (upload dc relay ip) (install-ssh-key ip) (reset ip) (wait dc relay)`), and the ssh/scp/sops one-liners become functions inside each recipe body.
The post-reset `sleep 10` moves into `wait` as a leading delay parameter (default 10 s) so `run` can be pure dependencies.
The full-chain recipe is named `run` (the old name, `bootstrap`, would read `just bootstrap mikrotik bootstrap`).
Alternative: `just := "just --justfile " + source_file()` as `tofu/mikrotik.just` does.
Rejected: it keeps recursion and re-roots `justfile_directory()`, the exact trap the hubitat justfile documents.

**D6. One secret source for MikroTik passwords.**
`wait` reads `tofu-password` from `secrets/hosts/<dc>-<relay>.sops.yaml`, the file `render` already uses to create the `terraform` user.
Reading the duplicate under `secrets/<dc>.sops.yaml` means `wait` can present a password the device was never given and time out with a misleading diagnosis.
The duplicate key is left in place (it may have other readers); this change only stops bootstrap from reading it.
The admin public key becomes `admin-pubkey := env("RBN_ADMIN_PUBKEY", home_directory() / ".ssh" / "id_ed25519.pub")` instead of `./id_ed25519.pub`, which `*.pub` in `.gitignore` guarantees can never be committed next to the justfile.

**D7. `rbn-bootstrap.rsc` is taken from `mikrotik/bootstrap/`, not the working-copy copy.**
The `mikrotik/bootstrap/` version is the committed one and carries the disabled SSH-host-key block with its "re-enable once confirmed innocent" note, which is operational state the stale copy dropped.
Content moves byte-for-byte; the only edit is none.
`upload` keeps staging `/relay-host.pem` so re-enabling the block needs no recipe change.

**D8. `bootstrap/kubernetes/` and `bootstrap/talos/` are tracked as they are.**
No file content changes.
The committed `kubernetes.nix`, `talos.nix`, and `modules/services/kubernetes/justfile` already read these paths.
The k3s/Talos seam is recorded in `bootstrap/AGENTS.md`: `cilium.yaml` and `flux-operator.yaml` are k3s `HelmChart` CRs (k3s's helm-controller pulls the charts), `flux-instance.yaml`, `flux-agekey.yaml`, and `cilium-values.yaml` are distro-neutral.
A Talos consumer supplies `cluster.inlineManifests` from rendered Helm output or a Flux `HelmRelease`, and that is the point at which a `k3s/` vs `talos/` split under `bootstrap/kubernetes/` earns its cost.
Alternative: split now.
Rejected: speculative structure with no consumer; two file moves later are cheap.

**D9. Tracking the iso-key public key, fencing the private one.**
`.gitignore` gains `secrets/keys/iso-key` as an explicit line; the existing `*.key`/`*.prv` patterns do not match an extensionless file, and git reports it as untracked-not-ignored today.
Observed during apply: this repo sets `snapshot.auto-track = all()` (the global `none()` is overridden), and the four files in `secrets/keys/` were invisible to jj only because of a stale file-state cache, cleared by `touch` or by editing `.gitignore`.
So "track one public key, leave the others untracked" is not a reachable state here: every non-ignored file under `secrets/keys/` is tracked once the cache refreshes.
`iso-key.pub`, `iso-key.age.pub`, and `1p-homelab.pub` are therefore all tracked, which matches the `.gitignore` policy that public material under `secrets/` is tracked; the private `iso-key` is the only file the new ignore line must cover, and it is verified ignored before anything is committed.

**D10. Rules and comments follow the files.**
New `bootstrap/AGENTS.md` (`paths: ["bootstrap/**"]`) holds: the per-target layout, the just entry points, D1's "only `bootstrap/nix/` is auto-discovered" constraint, D5's root-derivation rule, D6's single-secret-source rule, D8's seam.
Linked as `.agents/rules/bootstrap.md` (relative symlink, same shape as `hubitat.md`), both tracked.
`modules/services/kubernetes/AGENTS.md` loses its paragraph claiming `bootstrap/` is wholly outside the import-tree walk and instead points at the bootstrap rule.
`modules/hosts/AGENTS.md` gains one sentence: the installer image host lives at `bootstrap/nix/iso.nix`, the one exception to one-directory-per-host.
Comments updated: `modules/inputs.nix` (tool-tree list and template), `modules/devshell/shells.nix` (`gettext` for `bootstrap/mikrotik`), `tofu/mikrotik/users.tofu` (`bootstrap/mikrotik/justfile`).

## Risks / Trade-offs

- [A non-module `.nix` lands in `bootstrap/nix/` and import-tree tries to import it as a flake module] → `bootstrap/AGENTS.md` states the constraint; the existing convention (`_`-prefix to opt out) applies; `nix flake check`/`just bootstrap nix test` fails loudly at eval.
- [`ssh-keygen -p` on the stored `host-key` does not accept the PKCS#8 encoding] → verified in a task against a throwaway `openssl genpkey -algorithm ed25519` key before any host is touched; fallback is `openssl pkey` → PEM → `ssh-keygen`, still no Python.
- [Deleting `homelab bootstrap` breaks a caller] → `rg "homelab bootstrap"` across the repo shows only the ISO banner, which is rewritten.
  The docs site never documented it.
- [`just bootstrap …` muscle memory] → old `just bootstrap make` becomes `just bootstrap nix make`; `just --list bootstrap` shows the submodules.
  Root `just mikrotik` is unchanged, so the tofu helpers do not move under anyone.
- [Two in-flight changes modify the same `repo-layout` requirement] → this delta restates the requirement from the current main spec with the OpenTofu clause untouched; `tofu-root-at-repo-root` changes only that clause.
  Whichever archives second re-reads the main spec and re-applies its own clause.
  Noted in both proposals' Capabilities sections (this one; the other should be updated when it is next touched).
- [The MikroTik `run` chain as pure dependencies loses the explicit `>/dev/null` on render output] → `render` prints the path on stdout for human use; in the chain it is harmless noise.
  Accepted.
- [`nc -z` is not installed on the operator's machine] → macOS ships `nc`; NixOS hosts have `netcat` via the devshell if needed; the recipe names the missing tool.
- [Working-copy noise] → the main checkout has ~120 unrelated changed files (docs site, ai-tools, tofu/servarr).
  Tasks commit only the files this change names; `jj file track` is run per path, never on a directory glob that could pick up `secrets/keys/iso-key`.

## Migration Plan

Order matters for one reason: the flake must never be in a state where `bootstrap` is defined twice or not at all between commits.

1. Track `bootstrap/kubernetes/*`, `bootstrap/talos/*`, `secrets/keys/iso-key.pub`; add the `.gitignore` line.
   Commit.
   (`da-vcx-1`/`en-t65-1` now evaluate from a clean checkout; nothing else changes.)
2. Move the ISO aspect: create `bootstrap/nix/iso.nix`, delete `modules/hosts/bootstrap/bootstrap.nix`, change `modules/inputs.nix`, regenerate `flake.nix`, in one commit.
   Verify `nixosConfigurations.bootstrap` evaluates and `da-n1x`/`da-gr75` toplevel drvPaths are unchanged.
3. Just surface: `bootstrap/justfile`, `bootstrap/nix/justfile` (ISO recipes carried over, `facter` moved, `install` added), root justfile edits.
   Delete `modules/hosts/bootstrap/justfile`, root `facter`.
   Delete the stale `bootstrap/bootstrap.nix`, `bootstrap/iso.just`.
4. Python: delete `_bootstrap.py`, drop the import, drop `sopsy`, `uv lock`.
   Add `nixos-anywhere` to the devshell.
5. MikroTik: `bootstrap/mikrotik/{justfile,rbn-bootstrap.rsc}` from `mikrotik/bootstrap/`; delete `mikrotik/bootstrap/` (four entries) and the stale `bootstrap/mikrotik.just`, `bootstrap/rbn-bootstrap.rsc`.
6. Rules, comments, AGENTS.md, symlink.

Rollback: each step is one jj commit that moves files; `jj undo`/`jj abandon` restores the previous layout.
No live system is touched, so there is nothing to roll back outside the repo.
